# Native typography, vector graphics and professional audio

Research date: 2026-10-09. Scope: staged engineering recommendation, not an implementation or benchmark result. No dependencies were added for this research. The project remains proprietary; all selected third-party versions, features, fonts and assets require a locked dependency/license audit before integration.

## Typography and vector decision

Provisional pipeline: Rust text-layer specification → Parley layout → positioned glyph/vector scene → CPU reference overlay → shared Rust composition for preview/export. Prefer Parley for native creative text because its layout API separates shaping/layout from rasterization and fits the Linebender vector ecosystem. This is an engineering inference from API structure, not a measured quality advantage over cosmic-text. Animation/easing and rational-time evaluation remain Lumeryn code. Studio text fields may use ordinary Svelte DOM controls; project-output typography must not rely on browser layout.

Parley exposes reusable font/layout contexts, styled paragraph builders, shaping, line-breaking, bidi ordering and alignment. Reuse contexts and cache layout by text/style/font hashes; changing content/styles requires rebuilding layout. Its upstream stack includes Fontique, HarfRust, Skrifa and ICU4X. Main library licensing is MIT OR Apache-2.0; emoji/test assets have exceptions requiring separate review. [API](https://docs.rs/parley/0.11.1/parley/), [maintainer stack/license](https://github.com/linebender/parley).

cosmic-text is a credible alternative: integrated font discovery, fallback, shaping, layout, editing and optional Swash rasterization, under MIT OR Apache-2.0. Its current API uses HarfRust/fontdb and shared FontSystem/SwashCache resources. Prototype the same multilingual title corpus with both engines before freezing the choice; keep only one authoritative layout path in production. cosmic-text may win if a simpler cached-raster title implementation is materially easier and quality matches. Do not stack both layout engines or assume fonts selected on one machine will be identical elsewhere. [API](https://docs.rs/cosmic-text/0.19.0/cosmic_text/), [maintainer features/license](https://github.com/pop-os/cosmic-text).

Vello is a renderer family, not a text-layout engine. Current upstream distinguishes CPU Sparse Strips, GPU Sparse Strips and the experimental compute-centric research renderer. Start with vello_cpu as a candidate CPU reference/fallback, benchmark vello_gpu for acceleration, and do not make experimental compute rendering mandatory. Both CPU and GPU paths can serve the same constrained scene model. The family is MIT OR Apache-2.0. [Current renderer guidance](https://github.com/linebender/vello/blob/main/README.md).

Vello CPU 0.3.0 documents concrete limits: complex filter graphs can panic, simple filters are unsupported in multithreaded mode, and glyph caching is experimental. Validate scenes against the supported subset before rendering. Keep blur/glow/other effects in Lumeryn's effects abstraction; unsupported operations return errors. Its output pixmap is premultiplied RGBA8; the f32 processing option does not imply high-bit-depth/HDR output. [Vello CPU API/limits](https://docs.rs/vello_cpu/0.3.0/vello_cpu/).

resvg is suitable for static SVG asset import and cached rasterization through usvg/tiny-skia, under MIT OR Apache-2.0. It excludes scripting/events/animation and is not a timeline motion-graphics engine. Bound input bytes, dimensions, recursion and embedded-image sizes; restrict resource resolvers to approved project assets and prohibit network fetches. Preserve source SVG and parameters so a new raster size can be generated. Animation must use Lumeryn keyframes applied to supported scene properties. [resvg scope/license](https://github.com/linebender/resvg), [API](https://docs.rs/resvg/0.48.1/resvg/).

libass is a specialized ASS/SSA subtitle renderer, not the general title engine. Its own code is ISC licensed; the upstream page reports release 0.17.5. Review its font/render dependencies, Windows build and font licenses independently. A configured FFmpeg subtitles filter inherits the FFmpeg binary's actual license/build constraints, regardless of libass's permissive license. Use libass only for explicitly advertised ASS compatibility with reference fixtures; SRT/VTT caption text may map to Lumeryn's native caption layers. Preserve imported ASS semantics or warn/reject unsupported conversion. [libass](https://github.com/libass/libass), [license](https://github.com/libass/libass/blob/master/COPYING), [build dependency definitions](https://github.com/libass/libass/blob/master/configure.ac).

Application font policy: record font bytes/hash, face index, variation axes, shaping features, language, fallback choices and license. System-font discovery is convenient but insufficient for deterministic project output. Resolve missing-font substitutions visibly; do not silently change line breaks. Do not copy installed proprietary fonts into project packages. Bundle only licensed fonts after owner/dependency review. Validate Latin ligatures, Hindi/Devanagari, Arabic RTL, mixed bidi, combining marks, emoji and line wrapping. Rendering coordinates are project pixels; DPI affects Studio presentation, not project geometry.

## Audio recommendation

Reuse the controlled FFmpeg media adapter for decoding; do not add a competing broad decoder stack. Decode to bounded PCM chunks with explicit source sample rate, channel layout and source timestamp/sample origin. A raw PCM pipe alone loses timestamps, so initially support verified continuous streams with declared origin and reject discontinuities; later add a framed transport carrying timestamps. Account for encoder priming/trailing padding and reset decode state when seeking. FFmpeg sample-based trimming and timestamp-based trimming are distinct controls; test actual decoded boundaries. [FFmpeg audio trimming](https://ffmpeg.org/ffmpeg-filters.html#atrim).

Rust owns sample-index placement, channel mapping, gains/fades, pan, mute/solo, mixing and waveform statistics. Use integer sample frames and checked rational conversion from project ticks; do not round each video frame to an independently accumulated audio length. Half-open sample ranges and an explicit floor/ceil/nearest policy prevent cumulative drift. Project audio rate is explicit, initially48kHz; source audio stays immutable. Gain is unclipped floating-point DSP internally, with defined output clipping/limiting and metering; do not silently normalize overlap. Begin mono/stereo and reject unsupported channel layouts until matrices are tested. Tempo/time-stretch and pitch correction require later purpose-built DSP; resampling alone changes pitch.

Rubato supplies fixed-ratio FFT or adjustable sinc conversion. Preallocate processing buffers, handle filter delay/tails/short clips, and choose quality parameters explicitly. Use deterministic fixed conversion for source→project PCM; apply adaptive device-clock conversion only at the playback boundary. Its current API uses audioadapter layouts and provides allocation-free processing through preallocated methods; construction and buffers must happen before time-sensitive work. Disable optional logging in real-time paths. Rubato is MIT OR Apache-2.0. [Rubato API](https://docs.rs/rubato/5.0.1/rubato/), [real-time guidance](https://github.com/HEnquist/rubato), [manifest/license](https://github.com/HEnquist/rubato/blob/master/Cargo.toml).

CPAL provides device/configuration discovery and output callbacks; Windows defaults to WASAPI, with optional ASIO requiring additional drivers/toolchain and SDK review. CPAL is Apache-2.0. It is an I/O boundary, not the mixer, decoder or offline export clock. Select a device-supported sample format/rate/buffer configuration and report actual settings. Keep device startup, errors and unplug/recovery off the audio callback. CPAL's output timestamp distinguishes callback invocation from predicted playback time, so queue submission time must not be presented as the audible playhead. [CPAL platform/license](https://github.com/RustAudio/cpal), [CPAL callback timestamps](https://docs.rs/cpal/0.18.2/cpal/struct.OutputStreamTimestamp.html).

Application real-time policy: producer threads decode/resample/mix ahead into a bounded single-producer/single-consumer buffer; callback copies available data and writes silence on underrun. No allocation, locks, filesystem reads, decode, UI IPC or logging in the callback. Emit counters via nonblocking telemetry and retain generation IDs so stale pre-seek buffers are discarded. Handle variable callback sizes; never assume the requested latency equals measured end-to-end latency. Test shared-mode WASAPI first; ASIO/exclusive use is optional after licensing/device validation.

Use dasp selectively for sample/frame conversions, peak/RMS, envelopes or queue primitives where its contracts fit. Its MIT OR Apache-2.0 DSP modules do not supply a complete professional mixer, loudness standard compliance, time-stretching, clock authority or a demonstrated lock-free inter-thread queue. Audit concurrency semantics rather than equating a ring buffer type with callback safety. Implement small explicit DSP operations directly when clearer; do not add the umbrella crate with all features. [dasp API](https://docs.rs/dasp/0.11.0/dasp/), [manifest/license](https://github.com/RustAudio/dasp/blob/master/dasp/Cargo.toml).

## Audio/video clocks, waveforms and parity

Design: while playing with an audio device, derive presentation time from the playback timestamp plus sample-position mapping, including queued-buffer/device/resampler delay. Video follows that clock with a bounded drop/repeat strategy. If no audio device is available, use a Rust monotonic playback clock and declare degraded audio output. Pause/scrub/frame-step freeze or establish a new transport epoch; do not let UI timers drive authoritative time. Export always evaluates the immutable timeline by exact frame/sample ranges, without the wall clock or audio device.

The same deterministic mix function feeds offline export and playback-producer PCM. Device conversion is outside the shared mix graph. Compare pre-device PCM directly; encoded AAC results require decoded alignment and documented tolerances. A decode→FFmpeg-filter-only mix can be an early baseline, but cannot be claimed equivalent to the native mixer until comparison passes. Avoid silently maintaining two independent gain/automation implementations.

Generate waveform caches from source PCM: multilevel min/max and RMS buckets by integer sample range, plus channel layout/rate/hash/backend version. This permits large timelines to request a small visible range without rescanning every sample. Mix meters are live post-mix statistics, distinct from source waveforms. Silence, negative samples, clipping, DC offset and stereo channels need fixtures. LUFS/true-peak compliance requires a standards-aware meter later; sample peak/RMS are not substitutes.

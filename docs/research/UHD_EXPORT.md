# Local UHD export evidence

Reviewed and executed 2026-10-09. This implements unrestricted local UHD export for the existing supported Rust timeline, with no account, cloud, subscription, watermark or preview-quality dependency. It does not complete the other editor features in the Clipchamp inventory.

## Public settings and compatibility

`lumeryn_core::render::RenderOptions` is shared by CLI/service/Studio. JSON fields are `resolution` (`project`, `hd720`, `fhd1080`, `uhd2160`), `fps` (null preserves the rational project rate; otherwise 24/25/30/60), `codec` (`mpeg4`, `h264`, `h265`), `quality` (`draft`, `balanced`, `high`), `bitrate_kbps` (null or 100..200000), and `acceleration` (`cpu`, `auto`). Unknown fields fail. Missing options and `{}` retain the previous project-resolution/project-FPS MPEG-4/AAC CPU preset. No project database/schema migration is required. `lumeryn schema --kind render` exposes the actual shared type; bare `schema` continues exposing atomic `Batch`.

UHD means 3840×2160 for landscape, 2160×3840 for portrait, or 2160×2160 for square. Other project aspects fit inside the selected output with black padding, preserving aspect rather than stretching. The virtual project canvas is evaluated at final resolution: a true UHD source in a 1080p editing project is never reduced to 1080p before UHD export. An `upscaled` result flags source enlargement; enlargement is conventional Lanczos interpolation, not an AI/detail-recovery claim. Preview proxies, quality and monitor volume are absent from render inputs.

The current supported graph remains 1..64 contiguous, nonoverlapping video clips starting at frame zero on one track, verified matching source/project CFR, square pixels, zero-origin streams and SDR. Embedded audio or silence becomes stereo 48 kHz AAC at 192 kbps. Unsupported gaps, independent audio, layers, effects, transitions, HDR and other semantics fail explicitly until the authoritative Rust evaluator supports them. No second editor graph was introduced. Beyond-UHD dimensions, 8K, 10-bit HDR and mastering metadata are staged.

Cuts use original integer source frames before output-rate conversion. Output frame count is one exact rational ceiling of project duration into output frames. The first source frame is retained; output samples use the source frame at or before the output timestamp. The last picture can be held for less than one output frame; audio is padded/trimmed to that quantized duration. FFmpeg documents FPS rounding and end-of-stream handling, which require explicit selection rather than accepting implicit defaults. [Official filter documentation](https://ffmpeg.org/ffmpeg-filters.html#fps).

## Encoders, quality and hardware

MPEG-4 uses native `mpeg4`; H.264 CPU uses `libx264`; H.265 CPU uses `libx265` and MP4 `hvc1`. Missing/unusable encoders produce explicit errors, not a paid upgrade. CPU is the default. Auto enumerates candidate NVENC, QSV and AMF encoders, then actually encodes one black frame at the requested dimensions/rate/quality with an at-most-eight-second probe deadline for each candidate. A listing alone is not usability evidence. Failed hardware initialization selects an available, successfully probed CPU encoder. Hardware failure during the real export also retries CPU, recording the encoder and reason in the result.

Draft/balanced/high select MPEG-4 quantizers 6/4/2, x264/x265 CRF 28/23/18 with veryfast/fast/medium, NVENC p2/p4/p5 with VBR/CQ 28/23/18, and QSV global quality 28/23/18. AMF currently selects target bitrates 12/25/45 Mbps. An explicit bitrate overrides quality rate control; quality can still choose encoder effort. These encoder-specific values are not equivalent perceptual scores, guaranteed exact bitrate, two-pass sizing, or a CBR promise. [Official codec documentation](https://ffmpeg.org/ffmpeg-codecs.html).

CPU decoding/filtering and device upload remain in this implementation. NVIDIA documents GPU decode/filter/encode paths separately; using NVENC here does not establish hardware decoding, zero-copy, lower RAM/VRAM, or preview/export compositor parity for future effects. [NVIDIA FFmpeg integration](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/ffmpeg-with-nvidia-gpu/index.html). QSV/AMF initialization paths are implemented but were not successfully exercised on their physical devices in this acceptance run. Auto is compatibility selection, not a benchmark-driven fastest-encoder scheduler.

## Safety, progress and ownership

The existing trusted executable overrides, shell-free argument vectors, local-only input protocol, bounded captured output, worker deadlines, two decoder threads per input and two filter/encoder threads remain. x265 additionally limits pools/frame threads. Source paths are canonicalized and BLAKE3 is checked before and after processing. Existing output paths fail; a sibling temporary file is published with no-clobber only after codec/dimensions/FPS/frame count/zero-origin stereo48k audio checks and a complete decoded-output check. Generated artifacts are never inputs that can modify original media.

The service captures one immutable project revision, uses its existing one-render concurrency/16-job admission bound and cancellation/drop-child behavior. Actual `job_progress` events expose `validating`, `encoder_probe`, `encoding`, `verification`, `publication`, correlated with job ID/revision. No percentage is fabricated. Queued/running/completed/failed/cancelled events remain. Publication already completed cannot be retracted by later cancellation. The renderer's generic async progress callback adds no GUI dependency to the core.

## Executed media acceptance

Run `cargo test --locked -p lumeryn-core --test uhd_export -- --include-ignored --nocapture --test-threads=1`. Fixtures are generated locally in ignored disposable `.lumeryn-scratch/media` directories; no customer/downloaded footage or binary assets are committed.

The generated sources are actual 3840×2160 and 2160×3840 FFV1 test patterns at 60 FPS, twelve frames/0.2 seconds, with a PCM 1 kHz audio marker during 0.050..0.060 seconds. Eight actual UHD MPEG-4/AAC exports at 24/25/30/60 FPS produced exactly 5/5/6/12 frames. Full decode, exact dimensions/rate, source identity and no-clobber all passed. First decoded picture comparison at 192×108 RGB gave mean absolute channel error 0.018 landscape/0.017 portrait. A separate full-resolution regression compares a native UHD canvas with a 1080p project: all 8,294,400 decoded grayscale pixels match exactly, while a deliberately downsampled/upscaled reference changes 584,683 pixels, demonstrating meaningful source detail in the fixture.

H.264 CPU (`libx264`), H.264 Auto (`h264_nvenc`), H.265 CPU (`libx265`) and H.265 Auto (`hevc_nvenc`) each produced actual UHD30/6-frame files with an explicit 25 Mbps target. CPU/GPU measurements include initialization, encode, source hash and full verification; they are short-fixture compatibility measurements, not long-project throughput predictions. On the executed machine the four wall times were approximately 1.05, 1.07, 2.28 and 1.10 seconds respectively. MPEG-4 exports were approximately 0.57–0.78 seconds each. GPU is not assumed faster for every codec/workload.

Decoded AAC contains 10,240 samples/0.213333 seconds, including codec-frame padding, within one AAC frame (1024 samples) of the quantized video duration. The marker's energy center is 0.055003 seconds versus the intended 0.055 seconds; video and audio stream origins are zero. This verifies encoded timeline/sample mapping, not physical speaker/display synchronization. Fine-detail parity concerns the implemented scale/fit baseline; color-managed professional mastering and subjective quality evaluation remain separate work.

Fault-injection tests use a generated, locally compiled trusted FFmpeg adapter to simulate unavailable hardware at probe and at real encoding, while real FFmpeg encodes/verifies the CPU output. These establish fallback behavior without claiming a physical GPU failure. Service acceptance additionally checks stage order, immutable job revision, responsive edits and cancellation without published output.

## Licensing and alternatives

The executed external FFmpeg is `8.1.1-essentials_build-www.gyan.dev`, GCC15.2.0/MSYS2, configured `--enable-gpl --enable-version3 --enable-static` with `--enable-libx264`, `--enable-libx265`, NVENC, libvpl/QSV and AMF. This build is GPLv3, separately user-installed and not bundled or linked into Lumeryn. Lumeryn remains proprietary. Distributing that executable or a linked codec requires a separate exact-build licensing review, notices/source obligations and codec-patent review where applicable; subprocess separation is not a substitute for distribution review. FFmpeg's legal page explains how optional GPL/version3 components change the build license. [Official FFmpeg legal guidance](https://ffmpeg.org/legal.html).

A reviewed non-GPL FFmpeg build with native MPEG-4/AAC remains the baseline alternative. Platform H.264/H.265 encoders or a separately reviewed commercial encoder are future software alternatives when x264/x265 are unavailable; their presence is not currently advertised as supported CPU fallback. No new Rust dependencies or model downloads were introduced. Hardware driver/SDK redistribution must be reviewed separately if packaging changes.

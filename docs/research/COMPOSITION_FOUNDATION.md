# Composition foundation: independent audio and image holds

Research date: 2026-10-10. Baseline: local commit `194f261` (shared durable history and versioned clipboard); inspection began at its parent `ec74f79`. Scope: the smallest complete native/CLI slice that places verified music/narration independently beside held images and ordinary video. This document is an implementation proposal, not shipped capability acceptance. It changes no Rust, schema, dependency or source asset. No new benchmark, media render, device test or migration execution was performed for this research.

The owner-authorized eighteen-reference scope, [canonical CC task sequence](../roadmap/CLIPCHAMP_FEATURE_INVENTORY.md), [ADR 0001](../adr/0001-local-project-storage.md), [ADR 0005](../adr/0005-typography-audio.md), [ADR 0009](../adr/0009-semantic-scenes-explainers.md) and [ADR 0017](../adr/0017-shared-history-undo.md) remain governing context. Implement this within CC-02/04/05 foundations; do not substitute a new timeline or delay early semantic explainer work until recording, AI, advanced effects and every export format are finished.

## What exists and what must change

The source audit covers `lumeryn-core` model/time/media/render/storage, `lumeryn-preview` plan/decode/audio and the shared service contract. The baseline has stable IDs, integer project frames, reduced rational FPS, immutable BLAKE3 media references, strict typed commands, revision conflicts, dry-run/atomic batches, receipts, monotonic undo/redo, a native preview and verified UHD export. These are useful foundations, not independent composition support.

| Boundary at the baseline | Consequence for this slice |
| --- | --- |
| Schema 1 Project has one video-track ID; Clip has media ID, source-in, duration and placement measured in frames. | Audio-only placement is rejected; image duration is incorrectly constrained by video-frame metadata if treated as an ordinary video. |
| Video placement requires verified matching CFR. Metadata has optional Video/Audio; Audio records rate/channels/origin but no verified decoded sample length. | Introduce a distinct still-source interpretation and explicit audio range validation. Do not invent source duration from file size or nominal container bitrate. |
| Export and preview independently validate 1..64 contiguous visual clips starting at zero; both reject gaps/overlaps and nonzero stream origins/HDR/nonsquare pixels. | Extract shared supported-layout/time evaluation before adding new cases. Preserve explicit exclusions until proven. |
| Export trims embedded audio, converts to stereo 48 kHz, pads silence and concatenates. Preview decodes serial embedded audio directly at the device rate. | Their current independently generated audio programs are insufficient for independent overlap/gain/fades parity. |
| Preview monitor gain is applied at output; library audition lasts at most 30 seconds. Waveform thumbnails are an ephemeral presentation cache. | None of these is project music placement, persisted clip gain, mixing or a persistent content cache. |
| Graph snapshots are stored in project/history rows; storage version 1 is separate from graph version 1. Undo restores a validated historical graph under a new revision. | Every snapshot loading path must understand the new graph; changing only the current row breaks undo, checks and backups. |

Existing progress records contain actual baseline tests and measured limitations. The 105-test history milestone and earlier UHD acceptance do not verify these proposed source kinds or their audio mix.

## Minimum coherent behavior

The first delivery should let an external agent and a human use the same project service to import an inspected PNG/JPEG or supported mono/stereo audio source, place an image for an explicit frame duration, place/trim/move music or narration independently, set bounded gain/mute and linear fades, reopen/undo/redo, preview with sound and export with the same evaluated result. Imported bytes remain unchanged. Native library placement is this ordinary command flow, not a gallery-owned timeline.

Keep one nonoverlapping contiguous visual lane initially; allow bounded independently overlapping audio contributions. Image holds join the visual sequence with video; they are not multilayer composition or animated PNG support. Define project duration from the visual sequence for this narrow slice. An audio range extending beyond it must fail with the available range and an actionable instruction to shorten it or extend the visual sequence; do not silently truncate a music tail. No visual clips remains explicitly unsupported for MP4 in this slice. A later audio-only WAV/export family and black/background-gap semantics can extend this policy under discovery and tests.

Ordinary edit defaults are deterministic: image hold fits the canvas over the declared baseline black background; it has no source audio; audio gain defaults to unity and fades to zero duration. A music preset can propose a lower gain through a reviewable edit, but the engine must not guess that arbitrary imported audio is background music. CLI describes frames/sample units and constraints; beginner Studio can show seconds while preserving checked rational conversion. Unsupported channels, timestamp discontinuities, animated images and unknown color/alpha policies fail explicitly.

Avoid a general scene/effect/plugin system in this first change. Establish only the discriminants and evaluator seam required by real audio/still placement, then extend it for editable scenes/text/vectors/keyframes next.

## Rust-owned graph and command contract

Recommended schema-2 design uses typed source alternatives rather than unrelated optional fields: video range, image hold, and audio range. Video source ranges retain matching-CFR frames. An image hold has a verified image source plus timeline duration, with no source FPS or fake one-frame duration. An audio source range uses sample-frame indices at a declared source or canonical rate; distinguish interleaved scalar sample count from per-channel sample-frame count. Track identity, kind and role must be explicit; a Music/Narration label is descriptive, not an alternate mixer.

A smaller additive model with a separate audio collection is acceptable for the initial implementation if it has equally strict validation, stable globally unique IDs, a documented tagged source kind and no second editing authority. Do not add a broad track framework purely for future features. Schema/version discovery must distinguish old and new graphs even if Serde defaults make the current decoder technically accept old JSON.

Commands need explicit IDs, placement, source range, duration and settings. Apply import/place/trim/move/delete/gain/fade through the same revision-aware Edit/Batch service as existing edits. Stable IDs survive moves and property edits. Split a held image into two holds; split audio into exactly partitioned source ranges; video splits keep existing semantics. Duplicate/ripple/reorder commands must target a declared lane or explicitly reject new kinds until implemented; they must not silently shift independent music because the old implementation traverses every Clip. Video delete can preserve unrelated audio placement; any cross-track ripple behavior is a separate explicit operation.

Detaching video audio is a later explicit transaction unless included and verified now. It must create an independent audio object and suppress the original embedded contribution atomically, otherwise the result doubles sound. Link/group identity and restored split/source offsets need tests; a visible detached waveform is not proof.

Keep clipboard v1's current video/range semantics intact. A new source-kind clipboard requires a new version and authoritative validation. Existing receipt replay must keep working even if today's graph lacks the pasted source, as the history milestone already guarantees.

## Exact timing and one plan for both adapters

Extract a window-independent `CompositionPlan` in the headless Rust core. Build it from a validated committed graph and immutable media identities. It should expose visual segments, audio contributions, total frames, rational rate, project mix rate/channel layout, checked source/timeline ranges, gain/envelope parameters and supported-feature diagnostics. Preview-size/final-size selection is an evaluation parameter, not an alternate editing graph. Keep hashing and decoding off the UI callback and outside the writer lock.

Recommended canonical mix format is stereo float PCM at 48,000 sample frames/second. The exact mapping from project boundary frame `f` to sample frame is:

```text
B(f, R) = floor(f × fps.denominator × R / fps.numerator)
timeline audio range = [B(at, R), B(at + duration, R))
```

Use checked `u128` intermediates and checked conversion to bounded indices. Duration is the difference between the two absolute boundaries; never independently round every clip duration then sum it. At 30000/1001 FPS and 48 kHz, boundaries alternate fractional sample positions; this contract prevents cumulative drift. Source and timeline origins are different domains: source trim uses its declared decoded sample coordinate, while placement uses project samples. Padding silence cannot authorize reading beyond a verified explicit source range.

For source-rate conversion, define whether trimming happens before or after conversion and test the consequences at nonzero offsets. Recommended independent audio semantics retain native source sample coordinates, perform deterministic source-to-project conversion, compensate/record delay and tail, then place by exact canonical boundaries. Embedded audio uses the same contribution path. No timestamps, codec priming or gaps may be assumed away merely because a raw PCM pipe carries no timestamps. Preserve the zero-origin continuous-stream restriction initially; expand after measured fixtures.

Compute fade envelopes from absolute position within a contribution. For a nonzero fade of `N > 1` sample frames, specify endpoints (linear fade-in from 0 at the first sample to 1 at sample `N-1`; inverse for fade-out), reject overlapping fade ranges initially, and explicitly define/reject one-sample fades. Reject NaN/infinite gains and bound encoded numeric parameters. Sum in stable contribution order; choose a documented output policy, such as unclipped float internal sum with deterministic final clamp and a clipping counter. Never silently change other clips' gains as one source ends. Mute removes only that contribution; monitor gain remains outside the persisted mix.

Use the same plan and mix/envelope implementation for preview-producer PCM and offline export PCM. Device resampling/channel adaptation occurs after the canonical mix and cannot affect project timing or offline output. Random-access seek must equal sequential evaluation of the same range, discard stale generations and reset relevant decoder/converter state. CPAL remains only the device boundary; its documented callback/timestamp facilities do not supply a timeline mixer. [CPAL 0.18.2](https://docs.rs/cpal/0.18.2/cpal/).

## Backend options and current official evidence

Official FFmpeg rolling documentation was checked on the research date. It documents sample-count `atrim`, timestamp reset with `asetpts`, exact-sample `adelay` using the `S` suffix and all-channel delay. `amix` works with float input and defaults to normalization with a two-second dropout transition; blindly accepting these defaults changes gains as inputs end. `tpad` can clone frames. These are available primitives, not verified Lumeryn behavior. Probe the installed build and use generated allowlisted programs, never project-supplied filter strings. [Audio trim](https://ffmpeg.org/ffmpeg-filters.html#atrim), [delay](https://ffmpeg.org/ffmpeg-filters.html#adelay), [mix](https://ffmpeg.org/ffmpeg-filters.html#amix), [hold/padding](https://ffmpeg.org/ffmpeg-filters.html#tpad).

The image2 demuxer supports an explicit frame rate, looping and `pattern_type=none`; its default input rate is 25 FPS. A held image adapter must supply the chosen rate/duration, avoid interpreting `%` in a literal filename as a sequence, and retain bounded output/cancellation. Image identity comes from verified decoding/classification, not file extension alone. [FFmpeg image2 input](https://ffmpeg.org/ffmpeg-formats.html#image2-1).

| Alternative | Decision and required evidence |
| --- | --- |
| Shared Rust scheduler/mixer; existing FFmpeg decoders and encoders | Preferred long-term, matching ADR 0005. No broad new decoder dependency; small gain/envelope/sum logic is reviewable. Requires bounded chunk/queue design, conversion-delay tests, source-coordinate proof and partition-independent PCM. |
| Shared Rust plan compiled to one FFmpeg audio/filter adapter consumed by both preview and export | Acceptable bounded first implementation if it removes duplicate semantics and tests exact ranges/seek parity. Set normalization/dropout/clipping/channel policies explicitly. Render canonical PCM first; preview-only device conversion follows it. Do not maintain a second native mixer without comparison. |
| Direct libav bindings | Deferred; potential lower startup/copy cost needs measurements. Adds ABI, lifetime, threading, Windows DLL/build and isolated reviewed FFI obligations. Not required for music/image placement. |
| MLT worker/backend | Optional research only under ADR 0012; could evaluate a translated plan but is no substitute for authoritative Rust edits. Additional plugin licensing, build and parity/performance proof required. |
| Rust image decode and native CPU/wgpu composition | Useful next seam for image layers and semantic scenes. First held-image fit can reuse the existing media adapter; avoid adding a second wgpu device or unmeasured GPU/backend rewrite. |

For PNG alpha, define straight/premultiplied interpretation and flatten over the declared background consistently before baseline opaque export. Test transparent edge fixtures. Do not claim overlays, blend modes, general color management or animation from an image hold. Preview and export scaling may differ in resolution, but must use the same fit/canvas transform policy and a specified resampling algorithm when comparison matters.

## Explicit project/history migration

Graph version and SQLite storage version solve different problems. These additions can preserve existing tables while changing graph version; update storage version only if actual SQL layout/index requirements change. SQLite serializes writers and `BEGIN IMMEDIATE` obtains the write transaction before mutation reads; preserve the existing sole-writer service and expected-revision contract. [SQLite transactions](https://www.sqlite.org/lang_transaction.html).

Recommended explicit `project migrate` procedure:

1. Open a recognized old graph with its strict versioned DTO; unknown/future versions fail. Report current/target graph/storage versions and migration limits without persistent modification on ordinary inspection. Prepare a consistent new-path backup through the established backup operation.
2. Under the service's checked writer transaction, validate current project identity/revision, history continuity, schemas, snapshot/command byte/count bounds, receipts and FTS prerequisites. Refuse a stale revision or unsupported legacy record; no partial conversion.
3. Convert every stored project/history snapshot with one pure deterministic converter. Preserve project/media/clip IDs, the existing visual-track ID, all source paths/digests/ranges, durable and logical revisions, and default unity embedded audio/no fades. Derive any unavoidable new structural IDs deterministically from existing IDs, or avoid creating unused tracks during migration; do not generate different IDs when the same historical object is decoded again.
4. Preserve original command and receipt payloads byte-for-byte, including keys, revisions and object IDs. They bind historical requests and retry equality; reserializing them through a new command type can change equality/defaults and break retry. If command evolution requires normalization, introduce an explicit versioned receipt comparator with regression proof rather than silently rewriting audit data.
5. Update current graph schema column and all converted snapshots, rebuild derived metadata indexes, run invariants/history comparisons in the same transaction, and commit atomically. This representation-only migration should retain revisions and logical undo depth; ordinary edits after migration create the next revision. Refresh connected clients explicitly after commit so an unchanged revision cannot leave old graph state cached.
6. Reopen/check the migrated project, undo/redo across the migration boundary, recheck consistent backup/rebased history, and replay an old idempotency receipt. A malformed late history row or failed index rebuild must roll back the entire migration. Never probe/reimport media or invent missing digest/sample-length evidence during structural conversion.

A second valid strategy retains old historical JSON and uses one versioned decoder/converter on **every** load path: inspect, history restore, integrity, backup/rebase, render capture and export. This lowers write amplification but keeps permanent dual-schema complexity; do not mix it with current-only conversion accidentally. Eager explicit conversion is recommended for this small graph. Both strategies need the same legacy/corruption tests.

For actual future SQL table changes, use reviewed ordinary DDL/data copy in a transaction and rebuild affected indexes/triggers; SQLite documents the generalized ALTER TABLE procedure. Do not manually edit `sqlite_schema` or misuse its internal schema-version pragma to represent Lumeryn graph versions. [SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html), [pragma version distinction](https://www.sqlite.org/pragma.html#pragma_user_version). Backups must include committed WAL state; the documented Backup API or `VACUUM INTO` can create a consistent live snapshot. A filesystem copy of the main live file alone cannot establish that. [SQLite backup](https://www.sqlite.org/backup.html).

| Actual visuals/sound | Inspect held-image first/middle/last frames and boundaries, transparency/corner-marker/aspect fixtures, contact sheets and listening excerpts. Show source hashes unchanged and the exact captured project revision. |
| Preview/export parity | One plan drives both; compare lossless canonical outputs, random seeks and decoded final dimensions/rate/frame count/audio markers. Test each newly advertised editing family at genuine UHD landscape/portrait; baseline video-only evidence cannot cover images/mix. |
| Native/live service | CLI places/adjusts audio/image, Studio receives the committed revision; manual property edit uses the same command; actual new GPU-presented frame/audio metrics; seek/pause/project-switch stale generations and export cancellation. Launch alone is insufficient. |
| Required repository gates | `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --locked`, real configured media acceptance, full `./scripts/check.ps1 -Media -Deny` and the relevant actual-window native smoke. Lead records TASKS/PROGRESS and commits only verified work locally. |

Performance measurement targets, all unrun for this proposed slice: compare baseline versus new plan on the same host/build and source hashes; report ten-run cold/warm p50/p95 startup/first-frame/seek/plan-build/edit latency, hash/probe time, export elapsed time, peak working set, PCM queue high-water/underruns, decode count, UI-frame CPU and available GPU counters. Test 1/16/64 visual segments with 0/1/4/16 simultaneous audio contributions at 720p/1080p and selected UHD; start with conservative advertised limits and do not infer graph maximums are playback budgets. Measure cancellation/revision switches while hashing/decoding/exporting. Report unavailable GPU/VRAM counters as unknown.

Budget calculations guide measurement, not achieved performance: 48 kHz stereo f32 is 384,000 bytes/second before decoder/queue overhead; a ten-minute fully materialized mix is 230,400,000 bytes, so stream bounded chunks. One 3840×2160 RGBA frame is 33,177,600 bytes; queued frames multiply that. Reusing an unchanged held-image texture can avoid repeated decode/upload, but actual cache identity, lifetime, invalidation and measured benefit need proof. Hash a verified immutable source once per job/identity as the current trust model permits, and retain pre/post checks; do not introduce per-frame full-file hashing. Pre/post hashes retain the documented change-and-restore race limitation.

Suggested provisional acceptance targets are p99 mix-producer work below half the selected audio-buffer duration and no unexplained underruns in the measured ten-minute baseline; physical click/flash drift should stay within one project frame. These are targets from existing audio research, not achieved claims. A display/device test must separately establish audible synchronization. A faster backend is admissible only after identical semantics/quality, resource and cancellation evidence.

## Licensing, dependencies and next creative slice

No new dependency is required by this document. Keep FFmpeg/ffprobe user-installed and optional models/renderers out of minimal installation. The official FFmpeg legal page distinguishes its LGPL baseline from GPL-enabled builds; linking/redistribution obligations depend on the exact build and enabled libraries. The previously inspected local build's GPL status is not permission to bundle it. Review exact configure flags, enabled codec/filter dependencies, notices/source obligations and codec patent/distribution rights before shipping; original Lumeryn stays proprietary. [FFmpeg legal](https://ffmpeg.org/legal.html).

The audited library's CC0 audio/images and OFL fonts retain their pinned identities/notices; placement does not broaden their licence permissions or prove artistic suitability. Newly imported customer assets remain local references. Rubato/other conversion libraries require pinned dependency/cargo-deny review and measured delay/quality before addition; CPAL is already the native output boundary. No paid service, mandatory cloud store, MCP or embedded agent is introduced.

Next executable dependency order: shared plan and explicit graph/history conversion → independently editable audio plus image holds with CLI/service/native parity → native scene objects/text/vector/animation and narration cues → reusable semantic explainer components and scene-local review → editable Demo A. Image holds supply useful backgrounds/illustrations and audio supplies narration/music; they do not satisfy native diagrams, kinetic typography or a semantically editable explainer. Record the implementation decision in an ADR before calling the new graph/migration contract accepted. Record each actual limit and acceptance result beside the canonical tasks as the implementation settles.
